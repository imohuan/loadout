# DESIGN.md 设计文档审查（疏漏分析）

> 审查对象：`docs/DESIGN.md`（v1 初始设计）。结论分六类：内部矛盾、缺失定义、设计模糊点、承诺未覆盖、与实现的偏差、安全隐患。每项标注严重程度：🔴 高 / 🟡 中 / 🟢 低。

---

## 一、文档内部矛盾

1. 🔴 **日志格式自相矛盾**（第 9 节）：先写「输出…JSON 结构化」，紧接着又给出固定文本格式
   `时间 [等级] [源码相对路径:行号] 消息` 的示例。二者只能取一。当前实现取文本格式（遵循示例），JSON 结构化被放弃——文档应二选一并删除另一句。

2. 🟡 **schema_version 无定义**（第 13 节）：说「JSON 数据带 schema_version 字段用于迁移」，但第 5 节数据模型（5.1–5.11）没有任何一个文件定义该字段。要么在第 5 节补 `schema_version`，要么删掉这句。

3. 🟡 **backups 有目录无功能**（第 4.3 节）：`backups/` 注释写「一键备份命令的输出」，但全文没有任何备份命令的设计（无 CLI 子命令、无备份脚本）。

## 二、缺失的关键定义（实现时只能自行推断）

4. 🔴 **缺 REST API 规格**：第 3.3 只给了 `RouteSpec` 示例（`/v1/chat/completions`、`/mcp/github`、`/api/...`），第 11 节只列页面不列接口。管理后台实际有约 40 个端点（渠道/能力路由/MCP/工具状态/分组/密钥/skills/预设/设置/改密/测试），全部靠实现时自行推断，缺少一份 API 契约文档。这是最大的疏漏。

5. 🟡 **「默认渠道」语义缺失**：`config.UpstreamBaseURL`（NewAPI 地址）与 `channels.json` 的关系未定义——`/v1` 请求默认走哪个渠道？`capability_routes.channel_id` 为空时走谁？实现时定了「channel_id 空 → 用 UpstreamBaseURL 无 key」的规则，但文档没写。

6. 🟡 **视觉模型调用格式缺失**（7.2）：只说「批量抽取图片 → 一次调用视觉模型」，但多图如何组织（并列数组？）、`VisionDescriptionPrompt` 如何拼入、`image_url` 对象格式，均未定义。

7. 🟡 **reasoning 注入的 SSE 帧格式缺失**（7.4）：只说「流开头注入 reasoning_content 块」，无具体帧格式示例（如 `data: {"choices":[{"delta":{"reasoning_content":...}}]}`）。

8. 🟡 **MCP 端点认证时机缺失**（8.2）：header 认证在 streamable HTTP 的每次请求都校验还是仅握手时？header 名（默认 `X-Loadout-Key`）如何告知客户端？未定义。

9. 🟢 **request_id 细节缺失**（第 9 节）：说「每个请求生成 request_id」，但生成层（中间件？）、响应头字段名未定义。实现用了 `X-Request-Id`。

10. 🟢 **VisionCacheDir 常量缺失**（4.2 vs 7.2）：7.2 提到缓存目录 `~/.loadout/data/vision-cache/`，但 4.2 的 config 结构里只有 `VisionCacheEnabled`/`VisionCacheTTLHours`，没有目录常量。

11. 🟡 **插件自检结果的暴露方式缺失**（3.4 / 11 节第 8 项）：说「后台插件页展示自检结果、手动触发重新检查」，但没有定义对应 API（哪个端点返回自检结果？如何触发？）。

## 三、设计模糊点（实现时有歧义，曾因此踩坑）

12. 🔴 **「端点随配置自动生成」未区分静态/热更新**（8.2）：写「新增上游 MCP → 自动出现 `/mcp/github`；删除 → 端点消失」。但「自动」是启动时生成还是运行时热更新？当前实现是启动时静态挂载一次，运行时增删 MCP 需重启进程才生效——与「删除即消失」的字面不符。这是最需要澄清的设计点：要热更新就得改成 `/mcp/*` 动态路由（每请求查配置解析端点）。

13. 🟡 **同名工具冲突前缀的作用域**（8.6）：说「同名工具加 `来源_` 前缀」，但没说明是否考虑 disabled 的上游。曾导致实现与测试语义分歧（关掉 weather 后，github 的 `search_code` 是否还叫 `github_search_code`？）。文档应明确：前缀只在「当前启用工具」内计算。

14. 🟢 **channels.json 的 api_key 语义**（5.4 / 第 1 节）：这个 key 是「调 NewAPI 上游时用的鉴权 key」还是「NewAPI 里渠道自身的 key」？第 1 节说 NewAPI 做渠道管理，则应为前者，但文档未点明。

## 六、安全隐患（由文档头部备注引出）

26. 🔴 **`keys` 文件未忽略且已入库**：文档头部备注写「测试 AI Key 所在…`D:\Code\Git\loadout\keys` 这个文件夹下」。实际排查：
    - `keys` 是一个 **757 字节的文件**（非文件夹）；
    - 它**已被 git 跟踪**（`git ls-files` 命中），且 `.gitignore` 未忽略（`git check-ignore` 返回未忽略），当前还处于 `M`（modified）状态；
    - 一旦提交，测试用 API key 会进入 git 历史，存在泄露风险。

---

## 建议的处理优先级

1. **P0（安全）**：把 `keys` 加入 `.gitignore` + `git rm --cached keys`（停止跟踪，保留本地文件）；若已提交过，需评估是否清理历史。
2. **P0（设计澄清）**：明确「端点自动生成」是静态挂载还是运行时热更新；若需热更新，改造 `/mcp/*` 为动态路由。
3. **P1（补齐文档）**：补一份 REST API 契约（第 4 条），补 schema_version（第 2 条），统一日志格式表述（第 1 条）。
4. **P1（补实现）**：插件自检结果暴露给前端（第 15 条）、能力路由配置页（第 20 条）、MCP 工具开关/分组 UI（第 21 条）。
5. **P2**：config 文档同步 env 优先（第 24 条）、补 systemd 单元（第 18 条）、fixtures（第 23 条）。
