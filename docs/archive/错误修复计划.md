# 错误修复计划文档
## 一、概述
本次计划修复两个已定位的核心问题：
1. **错误信息重复前缀问题**：上游返回带「上游返回错误(N):」前缀的错误时，本层重复拼接导致双重/三重前缀
2. **openAIBaseURL 强制补 `/v1` 逻辑错误**：自动补全 `/v1` 导致无 v1 前缀的上游模型路径错误，出现 `/v1/v1/xxx` 类404

---
## 二、修复项1：错误信息重复前缀问题
### 1. 问题描述
- 上游网关（如 workbuddy、火山链路前置代理）本身已经会返回和 Loadout 格式完全一致的错误（已带 `上游返回错误(N):` 前缀）
- 后端 `upstreamErrorSummary` 逻辑是**无条件再拼一次相同前缀**，直接导致双重前缀
- 前端 `extractErrorSummary` 同时拿到后端 `error_message` 和 `error_body` 里的 message 字段时，会再次硬拼冒号，可能导致三层重复
### 2. 修复方案
| 层级 | 修改内容 |
|------|----------|
| 后端 | 修改 `upstreamErrorSummary` 函数：先判断传入的 `msg` 是否已经以「上游返回错误(」开头，是则直接返回 `msg`，不再重复加前缀；其他场景保持原有拼接逻辑 |
| 前端 | 修改 `extractErrorSummary` 函数：拼接前判断如果 `fbMsg`（后端返回的错误摘要）已经包含 `bodyMsg`（从错误体抠出的具体信息），或两者内容重复、`fbMsg` 已以 `bodyMsg` 结尾，则直接用 `fbMsg`，不强制拼接冒号 |
| 测试 | 新增单元测试用例，覆盖「上游返回带前缀错误」「上游返回纯消息错误」「多级嵌套前缀错误」三类场景 |
### 3. 实施步骤
1. 修改 `/plugins/model-gateway/service.go` 中 `upstreamErrorSummary` 函数，增加前缀判断逻辑
2. 修改 `/frontend/src/lib/errorExtract.ts` 中 `extractErrorSummary` 函数，增加重复内容判断
3. 在 `/plugins/model-gateway/proxy_test.go` 新增3条测试用例，覆盖上述三类场景
4. 手动构造上游返回带前缀错误的场景，验证日志和前端展示无重复
### 4. 验证标准
- 上游返回 `{"error":{"message":"上游返回错误(404)"}}` → 最终展示：`上游返回错误(404)`（无重复）
- 上游返回 `{"error":{"message":"上游返回错误(400): json: unknown field "client_metadata""}}` → 最终展示：`上游返回错误(400): json: unknown field "client_metadata"`（无双重前缀）
- OpenAI 官方等普通上游返回 `{"error":{"message":"Invalid API key"}}` → 最终展示：`上游返回错误(401): Invalid API key`（原有功能正常）
### 5. 风险点
- 需确保非中文上游的错误信息格式化不受影响，无截断或乱码
- 需兼容旧版本日志中已经存在的重复错误信息展示
- 前缀匹配需兼容括号内任意数字的情况，避免漏判

## 三、修复项2：openAIBaseURL 强制补 `/v1` 逻辑错误
### 1. 问题描述
- 当前逻辑强制给用户配置的 `base_url` 补 `/v1`，导致大量不需要 v1 前缀的上游模型（如 Claude、Gemini、厂商定制接口）路径错误，出现 `/v1/v1/chat/completions` 类404
- 用户明确要求：**不自动补全任何 v1 前缀**，`base_url` 完全按用户配置的原样使用，仅在末尾拼接最终接口路径（`/chat/completions`、`/responses`、`/messages` 等）
### 2. 修复方案
1. 完全移除 `openAIBaseURL` 函数中自动补 `/v1` 的逻辑，仅保留去除末尾斜杠的基础处理，`base_url` 完全按用户配置原样返回
2. 路径拼接逻辑保持不变：`trimRight(base_url, "/") + "/" + targetPath`
3. 前端渠道编辑页新增提示文案：「基础 URL 请填写到接口前缀的完整路径，如需 `/v1` 前缀请自行包含在 URL 中，系统不会自动补全」
### 3. 实施步骤
1. 修改 `/plugins/model-gateway/proxy.go` 中 `openAIBaseURL` 函数，删除自动补 `/v1` 逻辑，仅返回 `strings.TrimRight(baseURL, "/")`
2. 检查所有调用 `openAIBaseURL` 的代码位置，确认路径拼接逻辑未依赖自动补 `/v1` 的行为
3. 前端渠道编辑页新增提示文案，放在 `base_url` 输入框下方
4. 多场景测试验证：
   - 场景1：用户配置 `base_url = "https://api.example.com"` → 最终路径：`https://api.example.com/chat/completions`（无 v1）
   - 场景2：用户配置 `base_url = "https://api.example.com/v1"` → 最终路径：`https://api.example.com/v1/chat/completions`（保留用户自行配置的 v1）
   - 场景3：用户配置 `base_url = "https://api.example.com/api/v2/"` → 最终路径：`https://api.example.com/api/v2/responses`（无额外补全）
### 4. 验证标准
- 历史已配置带 `/v1` 的渠道功能完全不受影响，不需要用户修改配置
- 无 `/v1` 前缀的上游渠道请求路径正确，不再出现 `/v1/v1/xxx` 类404
- 所有接口类型（chat/completions、responses、messages）路径拼接正确
### 5. 风险点
- 需确保存量配置的所有渠道兼容性，无路径变更导致的业务中断
- 需提示用户新配置渠道时自行包含所需的版本前缀
- 需确认聚合模型、代理插件等所有依赖路径拼接的模块不受影响

## 四、总体上线验证流程
1. 本地跑通所有现有单元测试，确保无回归问题
2. 预发布环境验证：
   - 配置上游返回带前缀错误的渠道，验证错误信息无重复
   - 配置不带 `/v1` 的上游渠道，验证请求路径和返回正常
3. 上线后观察前10分钟错误日志，确认无新增路径错误或格式错误
4. 上线后24小时抽样检查错误日志，确认重复前缀问题完全消失
