## 【Bug 修复】ConfirmDialog 确认按钮无响应（reka-ui AlertDialogAction 事件不转发）

- **现象**：点确认按钮无任何反应、不调接口。
- **根因**：shadcn-vue-cdn 的 `AlertDialogAction`/`AlertDialogCancel` 底层是 reka-ui `DialogClose`，内置 `onClick → onOpenChange(false)`（点击只负责关框）；且 reka-ui `AlertDialogAction` 编译产物渲染时只传 props 不传 attrs，`@click` 绑定不可靠。结果点确认实际走 `update:open=false` → onOpenChange resolve(false) → 调用方 return，接口不执行。
- **修复**：ConfirmDialog footer 改用普通 `<Button variant="outline" @click="resolve(false)">` / `<Button :variant="destructive?'destructive':'default'" @click="resolve(true)">`（Button 事件绑定可靠），弃用 AlertDialogAction/Cancel。关闭由 resolve 自控；Esc/遮罩走 AlertDialog 根组件 `@update:open` → resolve(false)；resolve 消费后置空，关闭回环触发 resolve(false) 为 no-op，无竞态。
- **经验**：在 shadcn-vue-cdn（内置 reka-ui）里 AlertDialogAction/Cancel 只有"关闭"语义，别在其上绑业务 @click；业务按钮用普通 Button 自控。
- 验证：vue-tsc -b 通过。

## 日志合并能力：同 X-Request-Id 重试 UPSERT（plugins/route-log/service.go）

- **用户现象**：请求一次 auto-demo（熔断拦截 503），日志出现 4 条独立记录。
- **排查结论**：request_id 是 route_requests 主键，一次 HTTP 请求=一行；4 条 = 4 次独立 HTTP 请求（时间戳 23→25→29 递增 = 客户端退避重试）。"没被跳过时正常"= 请求成功 200 客户端不重试。后端聚合无 bug。
- **修复**：route-log Start 改 UPSERT（ON CONFLICT(request_id) DO UPDATE SET result='running'，保留首次 started_at）；Attempt 改 ON CONFLICT(request_id, step_no) DO UPDATE（按 step 覆盖）。客户端重试复用同一 X-Request-Id 时自动合并成一条日志。
- **测试**：TestRouteLogRetryMergesSameRequestID（同 request_id 重试 2 次 → 列表 1 条、attempts 按 step 覆盖、error_message 取最后）。全量 build + route-log/model-gateway 测试通过。
- 注：合并依赖客户端传 X-Request-Id；不传则行为不变（每请求一条）。

## 更新检测最终定案：npx skills check/update 同源（深度排查）

- **现象**：用户点检测更新，22 个技能全部报"官方暂无哈希（可能需重装）"。
- **排查链**：① 官方文档（Mintlify）说 check 走 POST add-skill.vercel.sh/check-updates；② curl 实测 API 直连 200 但返回 "No cached hash available"（forceRefresh 参数无效）；③ 翻 npx 缓存源码（~AppData/Local/npm-cache/_npx/*/node_modules/skills/dist/cli.mjs）确认：**1.5.22 的 check/update/upgrade 是同一个命令 runUpdate**（7511 行 `case "check": case "update": case "upgrade": runUpdate(...)`）——检测即更新，无纯预览模式；官方 check-updates API 已被弃用（新 CLI 用 GitHub API / well-known index.json + digest 对比）；GitHub 匿名 API 限流 60 次/小时是瓶颈（52 技能 5 源一次 check 即耗尽）。
- **最终实现**：`UpdateSkills()` 调 `npx skills update -y`，前后读 lock 对比 skillFolderHash 返回"实际更新了哪些"，随后 SyncAll 同步技能库。前端按钮改「检查并更新」，toast 报告更新列表/全部最新。
- **测试**：TestUpdateSkills（mock runCommand 改 lock hash 验证前后对比）、TestUpdateSkillsEmptyLock。
- 经验：GitHub 源技能更新走 GitHub API，限流时提示 `gh auth login` 提升配额。

## flex 容器溢出修复（SkillsView 详情模式）

- **现象**：详情模式（一个技能一行：名称+描述）描述文字超出 dialog 边界。
- **首次错修**：只在 button 行加 `min-w-0` —— 无效。chrome devtools 实测 list 容器 5230px 宽，dialog sw 5262px / ow 672px / overflowX: visible。button 的 min-w-0 已生效（min-width: 0px），但**外层祖先链**（form / space-y-2 / list）默认 min-width: auto 被内容撑大，dialog 自身也没截断横向。
- **真正修复**：三处一起加约束 —— `DialogContent class="sm:max-w-2xl! min-w-0 overflow-hidden"` + `<form class="w-full min-w-0 ...">` + button 行已有 `min-w-0`。修复后 dialog 672 / list 640 / btn 607 / desc visible 555px（自然 4591px，truncate ellipsis 生效）。
- **经验**：在 flex/block 容器里给单个子项加 min-w-0 解决不了问题，要看**整条祖先链**的 min-width 是不是 auto + 顶层有没有 overflow-hidden 兜底。chrome devtools evaluate_script 查 offsetWidth/scrollWidth + computed style 是最快的定位方法。
