## 聚合模型"目标不可用"错误信息带上真实原因（proxyRejectedLog 增强）

用户反馈：volcengine_auto 聚合请求失败时，转发日志显示 `no_available: 目标 "deepseek-v4-pro-ga-260813" 当前不可用`，文案笼统、看不出是免费额度用完。用户澄清："不是拦不拦截的问题，是错误信息的问题"。

1. volc-free-quota 把免费额度耗尽的模型写 `model_states`（status='cooling' + last_error）

3. model-gateway `proxyRejectedLog`（proxy.go:698）给每个目标写 skipped attempt，硬编码 `目标 %q 当前不可用`

**修复**：
- `plugins/model-gateway/proxy.go`：`proxyRejectedLog` 遍历目标时调用新增的 `unavailableReason(model, channelID)`，查 `model_states` 的 `last_error`（命中则原样带出，如"模型免费额度用完"），无 last_error 时按 status 落 `冷却中`/`已禁用`，都未命中回退默认文案；错误信息改为 `目标 %q 不可用：%s`。model-gateway 已有 `s.database` 可直接查，无需改 aggregate 接口。

## 转发日志架构调查（codegraph）→ 写档 ROUTE-LOG-ARCHITECTURE.md

**核心结论**：
1. **贯通三类请求（普通/虚拟/视觉）的参数是 `request_id`（X-Request-Id）**，不是 virtual_model。同一请求的视觉 attempt + 主链路切换 attempt 全挂同一 request_id 下，step_no 共享单调递增空间（视觉在前，`__route_step` 记录视觉最后 step，主链路从 step+1 续接，`__main_route_step` 独立计数防误判 action）。

4. **状态器实现位置结论**：真正三类都经过的共同点是 route-log 的 Start/Attempt/Finish（vision 也调 routeLog.Attempt），状态器挂这里最稳；且"是否继续"判断应以 DB 为准（查该组是否有更新且仍 running 的记录），不依赖进程内存（重启即失）。

## 转发日志"上游已成功但外层卡进行中"根因调查

**现象**：用户截图（17:36:07 volcengine_auto）显示子 attempt 「首次尝试 doubao-seed @ volcengine 已成功 13.69s」，但外层 request 一直「进行中」；90s+ 后才完成（97.13s）。

**根因（两个 bug 叠加）**：

1. **主链路 `proxyStream` 缺少 `[DONE]` 主动退出（核心根因）**：
   - `plugins/model-gateway/proxy.go:356-401` `proxyStream` 用 `reader.ReadString('\n')` 逐行读 SSE，**仅在 `err != nil`（io.EOF 或错误）时退出循环**，没有像视觉流 `plugins/vision/service.go:608 readVisionStream` 那样 `if data == "[DONE]" { break }`。
   - 豆包/火山引擎 HTTP/1.1 keep-alive 响应发完 `data: [DONE]\n\n` 后**不立即关闭连接**（留着复用），`ReadString('\n')` 阻塞等待下一个 `\n`，直到 Go HTTP transport idle timeout（默认 ~90s）触发 TCP 回收才返回 EOF。
   - 这正好匹配截图 13.69s（模型推理到 DONE）+ ~83s 等 EOF ≈ 97s 总耗时。
   - 视觉链路没有这个问题，因为它正确检测 [DONE] 并 break。

2. **流式 attempt 过早标 success（UI 误导）**：
   - `proxy.go:335` 在进入 `proxyStream` **之前**就调了 `proxyAttemptLog(... result="success")`，此时仅收到响应头、流刚开始。UI 显示"已成功 13.69s"是"收到响应头到现在的耗时"，不是真正流结束。
   - 正确做法：流式 attempt 先写 running 占位，`proxyStream` 返回后再写 finished success。

**影响范围**：所有走 SSE 流式输出的模型请求，总耗时被拖到 idle timeout（≈90s）才释放连接；SelfHeal 60s 阈值可能抢先误判为卡死。

**修复方向（待用户确认）**：
- proxyStream 解析 data 字段，遇 `[DONE]` 主动 break（向 vision 看齐）；
- 流式 attempt log 两阶段：proxyStream 前写 running、proxyStream 返回后写 success。

**架构教训**：聚合目标三种粒度（单 Key / Key 多选 / 渠道级）是**横切面**：attempt 行（已修）+ finish 行（这次补）+ 前端 attempt + 前端 final 都需要贯穿。前两轮 attempt 的修复几乎已完美，本轮最后一公里是 Finish + route_requests 不丢粒度。后续若有更多围绕 route_logs 的功能（比如 stats、filter），这套 schema 已具备。

**文档产出**：`docs/ROUTE-LOG-CHANNEL-REF.md` —— 请求日志渠道显示规范文档，按用户要求分三块：① 为什么之前不行（三轮根因：候选行主位错误 + attempt 落库丢粒度 + finish 落库丢粒度 + go:embed 需重编译重启）；② 如何修复（v17/v18 迁移 + contract + route-log + proxy + 前端全链路改动清单）；③ 显示规范（`模型名@渠道名(Key)`，三粒度优先级 渠道级>多选>单Key，自带哨兵分支，边界情况）。文档含数据模型、渲染优先级代码、关键代码索引表、开发/生产部署生效方式对照。
