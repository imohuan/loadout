## $smart 不可用根因调查（codegraph）+ BuildIndex 容错修复

用户反馈"执行 /mcp/$smart 不行"。用 codegraph（projectPath=D:/Code/Git/loadout，先 sync）追踪 SmartEndpointServer→invokeWith→callEntry→recordInvocation 调用链，找到 2 个真实缺陷：

- **缺陷 A（容错）**：`BuildIndex` 遍历 enabled servers 拉工具，任何一个 `ListTools` 失败即 abort 整个索引 → `ensureTools/resolveTools` 失败 → $smart 的 status/get/invoke 全挂且不埋点。用户配远程网关 mcp-gateway.app.baizhi.cloud，网络波动即触发。
- **缺陷 B（超时）**：`ListTools/CallTool` 无内置超时，BuildIndex 用 `context.Background()` → 上游挂起时 $smart 请求无限卡住（"没反应"）。

修复：
- `plugins/mcp-hub/service.go` BuildIndex：ListTools 包 `context.WithTimeout(ctx, config.McpListToolsTimeout)`，失败 → `s.warn` + `continue`（跳过坏上游，不 abort）。
- `core/config/config.go`：新增 `McpListToolsTimeout = 15s`（env: LOADOUT_MCP_LIST_TOOLS_TIMEOUT）。
- 补测试 `TestBuildIndexToleratesDeadUpstream`：2 好上游 + 1 坏（不存在的端口）→ BuildIndex 成功且只含好上游 4 工具。全插件测试通过。

**教训**：聚合网关的索引构建必须容忍单上游故障（fail-open），否则一个坏上游让整个 $smart/分组端点不可用，且错误调用不埋点导致统计盲区。codegraph trace 一次拿到完整调用链内联，比逐文件 Read 高效得多。

## ModelStatsPanel 时间计算 bug 修复（根因 = 后端 stats_models.go 硬编 UTC）

用户连续两次报错，截图显示折线图 X 轴只到 08-18、日历把 8-19 凌晨的请求（UTC 18 号 17:29）算到 8-18，箭头指向黑色"今天"块质疑"为什么算在 18 号"。

**根因**：`plugins/admin-api/stats_models.go` 三处用 `time.UTC` 计算 day key：
- `listRouteRequests` SQL cutoff：UTC "今天 00:00 - (days-1)"
- `aggregateModelStats` L175：`row.StartedAt.UTC().Format("2006-01-02")` 给每条记录打 day key
- `fillTrend` L231：UTC 算 X 轴 30 天序列

用户北京时间 8-19 01:29 发的请求 → UTC 8-18 17:29 → 后端 day key = `2026-08-18`。本地 0:00–8:00（GMT+8 区）的请求全部被算到前一天。前端日历 `isToday` 按本地时间 → 8-19 高亮但没数据（"今天"和"有数据"错位）。

**修复**（TDD）：
1. RED：新增 `TestAggregateModelStatsLocalDayKey`——UTC 8-18 16:00–18:30 的 4 条请求传 `loc=Asia/Shanghai` + 固定 now（UTC 8-18 18:00 = 北京 8-19 02:00），断言 day key = `2026-08-19` / 3979 tokens。编译失败（函数签名不匹配）= RED。
2. GREEN：`aggregateModelStats(logs, days, loc, now)` 接受 `*time.Location` + 注入 `now`（handler 传 `time.Now().In(loc)`，测试传固定值）；新增 `dayStart(t, loc)` 辅助；`listRouteRequests` cutoff 用 `dayStart(now, loc).AddDate(0,0,-(days-1)).UTC()` 转 UTC 时间戳；`fillTrend` 起点改为 `dayStart(now, loc).AddDate(0,0,-(days-1))`。

## sensitive-filter 降级策略变更（用户要求）

- 原行为：整体 stringify 替换后 `json.Valid` 校验失败 → 拒绝请求（fail-closed）。
- 用户改需求：**整体替换破坏 JSON 时不得报错**，降级为「只替换 messages 下的文本」——解析 JSON 结构，循环每条消息 content（纯字符串直接替换；分段数组只替换 type=text/input_text 块的 text 字段），重新序列化，天然合法。
- 实现：`replaceMessagesText(body, rules)`，用 `json.Decoder + UseNumber` 保数字原样；同时支持 messages（OpenAI/Claude）与 input（responses）两种键。
- 测试：TestJSONBreakFallback（引号破坏 JSON → 降级替换纯文本与分段 content）、TestMessagesFallbackRegex（降级路径正则仍生效；注意 JSON 序列化后引号变 `\"`，断言要用转义形式）。18 个全过。
- 前端文案同步：「替换后必须是合法 JSON 否则拒绝」→「整体替换若破坏 JSON 自动降级为只替换 messages 文本」。
