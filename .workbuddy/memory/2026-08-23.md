### SPA fallback 第二轮修复（Ctrl+R 后 /login 仍 404）
- **症状**：跑了上一轮修了 BundledAssetFileServer + SPAFallback 的 desktop binary，按 Ctrl+R 刷新 `/login` 路由还是 404（webview 内置错误页）。
- **根本原因**：上一轮 SPA fallback 里 `fs.ReadFile(fsys, "index.html")` —— 但 `apps/desktop/main.go` 的 embed 是 `//go:embed all:frontend/dist`，fsys 根路径是 `frontend/dist/*`，直接 ReadFile 必然 `file does not exist`，SPA fallback 退化为 `return handler`（透传）。**之前自称修好一半，其实整个 SPA fallback 都因为 index.html 读不到没生效**。Chrome MCP 跑 :3000 验证时之所以看着像 work，是因为 `core/servercore/server.go` 单独走 `spaFileServer`（fs.Sub("dist") + ReadFile），那条链是工作的，掩盖了 desktop 端 SPA fallback 的 bug。
- **修复**：`apps/desktop/backend/server/spa.go` 新增 `readIndexHTML(fsys)`：先尝试直读，失败就 `fs.WalkDir` 找 `index.html`、对所在目录 `fs.Sub`、再读。两种 embed 形态（`//go:embed dist` 和 `//go:embed all:frontend/dist`）都覆盖。
- **验证**：
  - 临时探测：`fs.ReadFile(frontend.Dist, "index.html")` → `FAIL file does not exist`；`fs.Sub(...) + ReadFile` → `OK 690 bytes`（bug 坐实）。
  - 编译 + go vet 都过。
- **教训**：embed.FS 的"根路径"取决于 `//go:embed` 之后的目录是不是 fsys 根。任何 fsys-based handler（不止 fallback）都要小心这个边界，读取嵌套目录前先 Sub。这次顺便把 vite-go-embed-trap skill 补上「Companion trap」一节，让下次有人踩坑一眼能看到。

## Desktop 子进程弹黑框修复（23:00-23:15）
- 现象：桌面 exe（windowsgui 无控制台）里 plugins/unifyai 执行 npx 命令时弹出黑色终端框。
- 根因：Windows 下父进程 windowsgui 不继承控制台，子进程（npx.cmd→cmd.exe→node）默认**新开控制台窗口**；需设置 `syscall.SysProcAttr{HideWindow: true}`（= CREATE_NO_WINDOW）。
- 实现：新增 `core/cmdutil` 公共包（`cmdutil.go` 带 `//go:build !windows` 空实现 + `hidewindow_windows.go` 真实现），**必须 build tag 分平台**——plugins 是跨平台共享（Linux server 编译），`HideWindow` 字段在 Linux syscall 不存在，直接写会炸 Linux 构建。
- 应用 4 处：unifyai/runner.go runCommandStream、unifyai/service.go PlatformInfo、skills/service.go runCommand 与 runCommandStream。
- 先例：apps/desktop/backend/singleton/mutex.go 早已用 `HideWindow: true`（desktop Windows-only 包，无需分平台）。
- 验证：Windows + Linux 双平台编译通过，unifyai/skills 测试全绿，desktop 重新打包 loadout-desktop-fixed.exe。
- 教训：**Windows 下 exec 子进程静默 = build-tag 分平台 + HideWindow**；跨平台共享包不能直接引 Windows-only 字段。
