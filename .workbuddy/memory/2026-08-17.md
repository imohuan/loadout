## 修复 MCP 管理页"工具列表"撑爆表格 UI
- 现象：上游服务器展开后，工具列表的描述把 `<table>` 撑到 11174px 宽（1280px 视口下），描述被裁切到屏幕外、按钮看不见。
- 根因（3 个叠加 bug，都在 `frontend/src/components/mcp/McpPanel.vue` line 339-356）：
  1. **shadcn-vue `<TableCell>` 默认带 `whitespace-nowrap`** — 整列所有文字强制不换行 → `<td>` 最小宽度 = 最长内容 → 表格撑爆。`white-space: nowrap` 还会继承到后代元素，line-clamp-2 直接失效（强制 1 行）。
  2. **`sm:max-w-[min(70vw,900px)]` Tailwind v4 不编译** — arbitrary value 里的 CSS `min()` 函数 v4 没识别，computed max-width 仍是 `100%`。改成 `sm:max-w-[min(70vw,_900px)]` 也无济于事（v4 语法变更）。
  3. **`wrap-break-word` 不是 Tailwind 工具类** — 正确的是 `break-words`（对应 `overflow-wrap: break-word`）。原项目里 2 处错用，下游用户的工具描述若有 URL / 长串可能撑列。
- 修法（3 行就修完）：
  - colspan `<TableCell>` 加 `whitespace-normal` 覆盖 shadcn 默认 nowrap
  - 描述容器从 `min-w-0 max-w-full flex-1 sm:max-w-[min(70vw,900px)] overflow-hidden` 简化成 `min-w-0 flex-1 overflow-hidden`（flex-1 + min-w-0 已经能约束列宽）
  - 描述 div 把 `wrap-break-word` 改成 `break-words`
- 验证（Chrome DevTools MCP）：1280px 视口 tableW 11174→1504，描述正确折成 2 行；800px 窄视口也无横向溢出。
- 经验：凡 shadcn-vue `<TableCell>` 里要塞 colspan 跨列内容（描述、长文案、JSON），**必须显式加 `whitespace-normal`**，否则会被默认 `whitespace-nowrap` 坑。

## 修复：/api/model-status 卡顿（model-health List 的 N+1 + 单连接死锁风险）
- 现象：调用 /api/model-status 一直卡。定位到 `plugins/model-health/service.go` 的 `List()`。
- 根因1（N+1）：原 List 逐渠道 `Check(id,"")` + 逐模型 `Check(channelID,model)`（内部 2 次 SQL）+ 再查一次 fail_count/last_error，查询数 ≈ 1 + 3C + 3M，模型多时上千次串行查询。
- 根因2（单连接）：`core/db/db.go` `SetMaxOpenConns(1)`，全进程只有一个 SQLite 连接，所有查询（含转发写 route-log、model-health 状态更新、CheckNow 定时器）串行排队抢这一个连接。
- 修复：把 List 重写为 3 次批量查询（渠道+渠道状态 LEFT JOIN / 模型目录 UNION / 全量 model_states），内存组装；`availabilityOf()` 复刻原 Check 分支语义（手动关闭 vs disabled/cooling、cooling 过期视为恢复、可用时 HealthStatus 硬编码 available）。
- 坑：SQLite MaxOpenConns(1) 下**不能同时打开多个未 Close 的 Rows**，否则互相等同一连接而死锁——批量查询必须「读完一个再查下一个」（拆成 listChannelStatus/listModelCatalog/listModelStates 三个 helper）。
- 验证：go build/vet 通过；新增 TestListAssemblesStatus 覆盖渠道 cooling、模型手动关闭、模型 cooling+fail_count/last_error/last_success_at/disabled_until、model_states 独有的模型；model-health/admin-api/route-log 测试通过。

## 模型网关自环死循环：渠道 base_url 指向网关自身
- 现象：访问 /v1/chat/completions 后日志狂刷：每次请求产生 N 条新的 `请求 ... request_id=...` + `检查 metadata keys=map[__route_step:2]` + `无法读取 __current_channel value=<nil>`，新请求的 `__route_step` 已经是 2。
- 根因（数据库直接确认）：channels 表里有个渠道 id=`6f3758eedcdbe862`，名字叫「本地模型 」（**末尾带空格**），`base_url=http://localhost:3000/v1` —— 正是 loadout 网关自身监听地址（`ServerAddr=":3000"`）。`forwardToModel` 用 `http.Client` POST `base_url+/chat/completions` 转发，结果转发回网关自己 → 新请求 → 再路由 → 再转发 → 死循环。`model_states` 里该渠道的 `fail_count=1872` 就是被循环打了上千次的铁证。
- 死循环运行机制（DB 模式）：原请求 → newapi 403、nid 403（两者 base_url 都是 `newapi.imohuan.shop/v1`，403 被 classify 为 auth → model_states 标记 disabled）→ 落到「本地模型」→ 自调用 → 新请求里 `resolveChannels` 跳过已 disabled 的 newapi/nid，recordAttempt 记 2 次 skip → `__route_step=2` → 只剩「本地模型」→ 又自调用。所以日志里新请求一上来就 `__route_step:2`、`__current_channel=nil`。`__current_channel` 那条 WARN（service.go:316-318）是噪音：非聚合模型本来就不设该字段，metadata 非 nil 就误报。
- 修复：用户直接删了那个渠道（DB 里已无此 id）。建议补一道**自环检测守卫**：`forwardToModel` 解析渠道 base_url，若 host 是 localhost/127.0.0.1 且端口等于 `config.ServerAddr` 的端口，跳过并 WARN，避免再次误配把服务打挂。

- 根因：上次 #1 修复时把 `tryAggregateFailover` 写成"内部递归 + `_ = s.forwardToModel(...)` 抹掉 error"——当所有目标都试完仍失败，helper 返回 `true`，caller 走 `return nil`，`HandleChat` 主循环以为成功直接 `return` 退出，**没调 `finishRouteLog`**，row 永远留在 `running`。
- 修法：把 `tryAggregateFailover` 改回纯透传——只发事件 + 返回 `(*RetryPayload, bool)`，递归和错误传递都还给 caller。caller 看到 `(retry, true)` 就 `return s.forwardToModel(w, r, retry.Pipe, ...)`（递归的 error 自然透传到 HandleChat 的"all failed"路径调 finishRouteLog）；看到 `(nil, false)` 就按失败返回。no-channels 分支与原 all-channels-failed 分支都走同一套。
- 回归测试：`model-gateway` 加 `TestHandleChatAggregateAllTargetsNoChannel`，验"聚合所有目标都没渠道"必须返回 502（之前会漏 finishRouteLog 返 200）。
- 数据库里那张 1f5fa3a59488a435 是真实僵尸，已存在的孤儿 `running` 行（最早 12:50:26 一批）需要手动清或加后台清扫。

## 修复：MCP "测试工具" 弹窗全局滚动条
- 现象：调 `web_search_exa` 返回一大段 JSON 时，整个**页面**（背景表格）出滚动条，能滚到看不见 dialog。
- 根因：`frontend/src/components/mcp/McpPanel.vue` line 720 的 `<DialogContent class="max-h-[calc(100dvh-2rem)] overflow-y-auto sm:max-w-2xl!">` —— dialog 自己滚动可，但当 header + 表单 fields + 256px pre + footer 合计超 `100dvh-2rem` 时，dialog 默认 `grid` 布局没用 flex 约束溢出，导致 dialog 撑破 viewport → 页面出滚动条。
- 修复（参考 `ModelTestView.vue` 已有的同款写法）：
  - `<DialogContent class="flex max-h-[calc(100dvh-2rem)] flex-col overflow-hidden sm:max-w-2xl!">` —— 外层只裁切，不滚动
  - 中间 body `<div v-else class="min-h-0 flex-1 space-y-4 overflow-y-auto">` —— 占据剩余高度，内部独立滚动
  - `<pre class="max-h-80 overflow-auto ...">` —— JSON 块保持局部滚动（max-h 64→80，多给点空间）
- 经验：**shadcn-vue-cdn 的 `<DialogContent>` 默认 `grid` 布局，配合 `overflow-y-auto` 不能保证裁切**。要"内部滚动而非全局滚动"的 dialog，正解是 dialog 本体 `flex flex-col overflow-hidden` + body `min-h-0 flex-1 overflow-y-auto`（`min-h-0` 是关键，否则 flex item 不会被压缩）。
